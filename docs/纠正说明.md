# 八十、最终决定

你提出的：

```text
Q1 = C
Q2 = A
Q3 = B
```

我建议改成：

```text
Q1：
不是 A/B/C，
而是 G0~G3 Validation Gate。

Q2：
先 Git Freeze，
然后立即建立最小 Metrics/Probe，
再做 StrokeFrame。

Q3：
不要统一采用 MAE=5/255。
根据测试层级分别设阈值。

Q4：
Reference 不做完整 CPU Renderer，
只做 CPU Reference Sampler。

Q5：
Shadow 不实时双跑，
采用 Record + Replay + Diff。

Q6：
Active Tile 延后到 Wet Solver 性能阶段。
```

这才是目前对这个项目最稳妥、技术上也最严谨的路线。

最关键的一点是：

> **我们不是在“选择严谨方案还是轻量方案”。**
>
> 我们是在把原来的“大而重的完整计划”压缩成“轻量但不可缺失的正确性 Gate”，然后再逐步增加复杂的材料物理。

这样既不会把项目拖入你担心的 27-PR 马拉松，也不会因为为了“快”而重新退回到**肉眼调 Shader、没有证据、出了问题不知道哪一层错了**的老路。

而且，OpenGL ES 3.0 本身对浮点运算有明确的精度约束，但具体 GPU 行为仍需实测；RGBA16F 也是 GLES 3.0 的标准 sized color format，因此你们完全应该把“GPU 可达误差”通过小型基准测试实际测出来，而不是先假设一定有 3~5/255 的误差。

Mixbox 则更应该被隔离在自己的 Gate 里：它的官方实现确实包含 sRGB/linear 转换和 LUT/latent 处理，因此其误差模型与“PNG 原始采样是否准确”完全不是同一个问题。

**所以我现在最推荐你做的下一件事，不是让这个助手立即写 StrokeFrame，而是把它要求的“第一轮 G0~G3 实施任务”固定成一份非常严格的任务单，然后再把你现有的真实源码交给它。**这样它后面每一步都只能在我们定义好的边界里推进。
